1. DESCRIPCION GENERAL
=====================================================================

SITTI es una plataforma web para registrar, consultar, asignar,
actualizar y dar seguimiento a solicitudes de soporte tecnico. El
sistema separa las funciones de Usuario, Tecnico y Administrador,
permite administrar el ciclo de vida de los tickets y conserva la
informacion en PostgreSQL.

El proyecto esta compuesto por:

- Frontend desarrollado con React 19, React Router 8, TypeScript,
  Tailwind CSS y Vite.
- Backend desarrollado con Node.js, Express y TypeScript.
- Persistencia en PostgreSQL 16 mediante Prisma ORM.
- Autenticacion basada en JWT.
- Hash de contrasenas mediante bcrypt.
- Ejecucion local y despliegue de desarrollo mediante Docker Compose.

Objetivos principales:

1. Centralizar las solicitudes de soporte.
2. Asignar tickets a tecnicos responsables.
3. Permitir el seguimiento por estado, prioridad, area y categoria.
4. Proporcionar vistas diferentes segun el rol del usuario.
5. Mantener historial, comentarios, adjuntos y notificaciones.
6. Facilitar la consulta de informacion operativa para administracion.

2. DISENO
=====================================================================

2.1 Usuarios del sistema

USUARIO:
- Inicia sesion.
- Registra nuevos tickets.
- Consulta los tickets que solicito.
- Consulta el detalle y el estado de sus tickets.
- Consulta notificaciones y su perfil.

TECNICO:
- Consulta el tablero de trabajo.
- Consulta la cola de tickets.
- Consulta tickets asignados, pendientes y resueltos.
- Actualiza el estado, prioridad y responsable de un ticket.
- Consulta notificaciones y su perfil.

ADMINISTRADOR:
- Consulta el tablero general.
- Consulta y administra todos los tickets.
- Administra usuarios, areas y categorias.
- Consulta la vista de reportes.
- Accede a configuracion y perfil administrativo.

2.2 Reglas funcionales principales

- Cada usuario pertenece a un rol y a un area.
- Cada ticket tiene un solicitante obligatorio.
- Un ticket puede tener un responsable tecnico o permanecer sin
  asignar.
- Cada ticket pertenece a un area, categoria, prioridad y estado.
- El folio del ticket es unico.
- La fecha de creacion se genera automaticamente.
- La fecha de actualizacion se modifica automaticamente mediante
  Prisma.
- La fecha de cierre es opcional y se utiliza al cerrar el ticket.
- Los comentarios, adjuntos, historial y notificaciones se relacionan
  con el ticket.
- Las relaciones criticas utilizan restricciones de integridad
  referencial.

2.3 Estados del ticket

- ABIERTO: ticket creado y pendiente de atencion.
- ASIGNADO: ticket asignado a un tecnico.
- EN_PROCESO: ticket en atencion.
- PENDIENTE: requiere informacion, autorizacion o una accion externa.
- RESUELTO: la solucion fue aplicada.
- CERRADO: el ciclo de atencion finalizo.

3. ARQUITECTURA DEL SISTEMA
=====================================================================

La arquitectura es de tres capas: presentacion, servicios y datos.
El navegador consume una API REST protegida con JWT. El backend
consulta PostgreSQL mediante Prisma.

                         USUARIO
                           |
                           v
                 NAVEGADOR WEB
                 localhost:5173
                           |
                    HTTP / REST + JWT
                           |
                           v
             FRONTEND REACT / REACT ROUTER
             - Rutas por rol
             - Componentes reutilizables
             - AuthContext
             - Servicios API
             - Tailwind CSS
                           |
                    HTTP / JSON
                           |
                           v
             BACKEND EXPRESS / TYPESCRIPT
             localhost:3000
             - Rutas
             - Controladores
             - Servicios
             - Middleware de autenticacion
             - Validadores
             - Manejo de errores
                           |
                    Prisma ORM
                           |
                           v
                   POSTGRESQL 16
                   sitti_db

Componentes principales:

Frontend:
- app/routes/: pantallas y rutas de usuario, tecnico y administrador.
- app/components/: componentes comunes, formularios, dashboard y
  tickets.
- app/context/AuthContext.tsx: estado global de autenticacion.
- app/services/api.ts: cliente HTTP y envio del token.
- app/services/*.service.ts: acceso tipado a los recursos de la API.
- app/types/: tipos TypeScript.

Backend:
- backend/src/routes/: declaracion de endpoints.
- backend/src/controllers/: recepcion de solicitudes y respuestas.
- backend/src/services/: reglas de negocio y acceso a datos.
- backend/src/middleware/: autenticacion, roles, errores y carga.
- backend/src/validators/: esquemas de validacion.
- backend/src/config/: variables de entorno y conexion Prisma.
- backend/prisma/: esquema, migraciones y seed.

Flujo de una solicitud:

1. El usuario interactua con una vista del frontend.
2. El servicio correspondiente genera una solicitud HTTP.
3. El cliente API agrega Content-Type y Authorization cuando existe
   una sesion.
4. Express recibe la solicitud y ejecuta middleware.
5. El controlador valida la entrada y llama al servicio.
6. El servicio consulta o modifica PostgreSQL mediante Prisma.
7. El backend devuelve JSON.
8. El frontend actualiza la vista, muestra resultados o reporta el
   error al usuario.

documentacion distribuida.

El esquema se encuentra en:
backend/prisma/schema.prisma

Las migraciones se encuentran en:
backend/prisma/migrations/

1. Levantamiento del contenedor PostgreSQL.
2. Generacion del cliente Prisma.
3. Aplicacion de migraciones pendientes.
4. Ejecucion del seed de catalogos y datos de prueba.
5. Inicio del backend.

cd backend

npm run db:studio

11. AUTENTICACION Y AUTORIZACION
=====================================================================

11.1 Autenticacion

1. El usuario envia correo y contrasena a POST /auth/login.
2. El backend busca el usuario por correo.
3. bcrypt compara la contrasena recibida con password_hash.
4. Si es valida, se genera un JWT.
5. El backend devuelve token y datos basicos del usuario.
6. El frontend almacena el token en localStorage.
7. Cada solicitud protegida envia:

Authorization: Bearer <token>

11.2 Persistencia de sesion

Al cargar la aplicacion:

1. AuthContext busca auth_token.
2. Si existe, configura el cliente API.
3. Solicita GET /auth/me.
4. Si el token es valido, restaura el usuario.
5. Si es invalido o expiro, limpia el token y muestra login.

11.3 Autorizacion

- El frontend organiza las vistas por rol para la experiencia de
  usuario.
- El backend utiliza middleware de autenticacion y middleware de
  roles para proteger operaciones.
- Las operaciones sensibles deben validar siempre el rol en backend;
  ocultar una opcion en frontend no sustituye la autorizacion.

11.4 Medidas de seguridad

- Contrasenas almacenadas como hash bcrypt.
- Tokens JWT con expiracion configurada.
- CORS restringido a origenes locales de desarrollo.
- Variables sensibles fuera del codigo fuente.
- Validacion de entrada con esquemas.
- Separacion de responsabilidades por middleware.

Para produccion se recomienda:

- Cambiar secretos y credenciales de desarrollo.
- Usar HTTPS.
- Rotar JWT_SECRET.
- Configurar CORS con dominios reales.
- Aplicar limites de solicitudes.
- Definir almacenamiento seguro para adjuntos.
- No usar contrasenas incluidas en ejemplos.

Frontend service
      |
      | api.post("/auth/login", datos)
      v
Express route
      |
      v
Controller -> Service -> Prisma -> PostgreSQL
      |
      v
JSON response
      |
      v
React state / pantalla

Errores:

- Si la respuesta no es 2xx, ApiClient intenta leer error.error.
- El servicio lanza una excepcion.
- La pantalla debe mostrar el mensaje de error y conservar la
  posibilidad de reintentar.

  -H "Content-Type: application/json" \
  -d '{"correo":"usuario.ventas@sitti.com","password":"password123"}'

- Logout y limpieza de localStorage.

16.3 Pruebas de tickets

- Crear ticket con datos validos.
- Rechazar datos obligatorios faltantes.
- Listar todos los tickets.
- Listar tickets del usuario autenticado.
- Consultar un ticket existente.
- Consultar un ticket inexistente.
- Actualizar estado, prioridad o responsable.
- Eliminar un ticket segun permisos.
- Verificar folio unico.
- Verificar relaciones con catalogos.

16.4 Pruebas de interfaz

- Acceder al dashboard de cada rol.
- Verificar que la navegacion cambie segun el rol.
- Verificar rutas de detalle.
- Validar estados de carga y error.
- Validar diseño movil, tablet y escritorio.
- Validar modo oscuro.
- Validar formularios y mensajes de validacion.

16.5 Comandos de validacion

Frontend:

npm run typecheck
npm run build

Backend:

cd backend
npm run build
npm run lint
npm test

La suite automatizada de backend se ejecuta mediante Vitest. Si no
existen casos de prueba en el entorno actual, la validacion debe
complementarse con las pruebas manuales descritas arriba.

Estado actual y pendientes de integracion:

- La estructura visual de reportes existe en frontend.
- La capa de reportes del backend requiere completar consultas,
  controladores, rutas y conexion con la pantalla.
- Las rutas de areas y categorias deben registrarse en app.ts si se
  desea exponerlas por API desde el backend actual.
- Debe ejecutarse una ronda de pruebas automatizadas y de aceptacion
  con la base local antes de declarar el sistema listo para
  produccion.
- Deben reemplazarse credenciales y secretos de desarrollo antes de
  cualquier despliegue publico.

SITTI cuenta con una base tecnica funcional para la operacion local:
frontend, backend, autenticacion, persistencia y gestion de tickets
estan organizados e integrados. La principal actividad de cierre
documentada es completar y validar la integracion de reportes,
catalogos expuestos por API y la matriz formal de pruebas para
produccion.
